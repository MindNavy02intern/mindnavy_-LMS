## Course Creation Wizard (doc §3) — 6 steps, autosave draft = `course.createDraft`/`course.update`
1. **Basic information:** title, subtitle, description, category→`['categories']`, tags, language, difficulty, thumbnail upload.
2. **Course builder:** sections → lessons → topics → modules → learning outcomes. Lesson types: video, text, PDF, assignment, quiz, live session, SCORM, downloadable resource.
3. **Content upload:** videos, PDFs, ZIP, images, audio, attachments → backend pipeline (file validation, video encoding, virus scan, compression, verification) → job status `['uploads', jobId]`.
4. **Settings:** free/paid, pricing, enrollment limit, visibility, certificate enabled, drip content, access rules, SEO.
5. **Preview:** desktop, mobile, student experience, quiz preview, video playback test (read).
6. **Save or submit:** Save draft→`course.update` (→ §5.4 draft row) · Submit for approval→`course.submitForApproval` (→ §5.4; system validation: thumbnail, lessons, videos, quiz, description, settings).

## Approval & Admin Review (doc §4–§5)
Submit → status Pending Approval → admin notification + task → review queue → open details.
Review areas: title, lessons, videos, quizzes, assignments, resources, attachments, certificate settings, accessibility, copyright.
Decision: Approve→`course.approve` (publish, live, visible) · Reject→`course.reject` (reason, notify instructor) · Request changes→`course.requestChanges` (return to instructor). All → audit.

## Tab: Certificates (`?tab=certificates`) — `['certificates']` + `['certificate-templates']` (doc §9)
**Status: `[built]` 2026-07-17 — v1 (manual issuance only; auto-trigger rules below are NOT wired yet)**.
`CertificatesTab.tsx` (sub-tabs: Issued Certificates / Templates) + `certificatesApi.ts` + `certificateTemplatesApi.ts` + `publicCertificatesApi.ts` + types `certificates.ts`. No CERTIFICATES_CONTRACT.md exists in the repo (checked root/docs/git history, same as Quizzes) — shapes reverse-engineered from backend source, verified live against a running server.
Builder: templates (name + layout: title/body/primaryColor/accentColor/signatureName/signatureTitle — NO logo field, v1 scope explicitly excludes it, SSRF risk deferred to the existing uploads sign→confirm flow in v2), insertable `{{studentName}}`/`{{courseTitle}}`/`{{date}}` chips in the body editor, PDF download (blob+Bearer fetch, never a plain `<a href>`), QR verification via `/verify/:code`.
**Template edit is the one PATCH in this app that does NOT diff** — `layout` REPLACES the whole object server-side (missing keys reset to defaults), so the edit form always sends the complete current layout, never just the changed fields.
`studentName`/`courseTitle` on a certificate are issue-time snapshots (rendered exactly as received, never re-joined against the live user/course record); `templateName` is NOT a snapshot — it's read live off the relation, so a template rename or delete changes what already-issued certificates display.
Trigger rules (course completion · passing grade · path completion · session attendance → fire `certificate.issue`) are a documented v2 decision, not code — v1 issuance is manual only via the "Issue Certificate" dialog, but `issueCertificate()` on the backend is already the single entry point future auto-triggers will call (→ IMPACT §5.8).
Public verify page: `/verify/:code`, standalone route (no `ProtectedRoute`, no `AdminLayout`) — `PublicVerifyPage.tsx`, mobile-first, zero auth dependency. Always renders one of three states from `data.status`: valid (✅ studentName/courseTitle/issuedAt) / revoked (⚠️, no details) / not_found (❌).
Mutations: `certificateTemplate.create` / `certificateTemplate.update` / `certificateTemplate.delete` (local: `['certificate-templates']`, `.update`/`.delete` also invalidate `['certificates']` since `templateName` is live not snapshotted) · `certificate.issue` / `certificate.revoke` / `certificate.reissue` (→ §5.8). The `certificate.reissue` + `certificateTemplate.*` mutation IDs were already named in this blueprint doc, but their IMPACT_MAP §5.8 rows and invalidation.ts entries did not actually exist yet — added in this change, not merely mirrored from a pre-existing row (flagging per the "verify before trusting a claimed pre-existing artifact" pattern from this session).

## Tab: Content Library (`?tab=content`) — `['content-library']` (doc §11)
**Status: `[built]` 2026-07-21 — v1**, contract `CONTENT_LIBRARY_CONTRACT.md`. `ContentLibraryTab.tsx` + `contentLibraryApi.ts` + types `contentLibrary.ts`. Extends the EXISTING `course_contents` table — same table the LM Overview "Content Statistics" tiles read (B2 single-owner rule), so those tiles update automatically as items are added/deleted here.
Upload is the same sign → direct PUT → confirm pipeline as course thumbnails/videos, but via this feature's OWN `/content/sign` + `/content/confirm` endpoints (not the shared `/uploads` ones). `type` is 100% server-derived from MIME at confirm — no type picker exists in the upload form. Uploadable in v1: VIDEO/DOCUMENT/PDF/AUDIO/IMAGE; QUIZ/SCORM are valid FILTER-only values (legacy rows), never offered as upload targets — enforced structurally via a separate `UploadableContentType` subset. Size cap is read from the real `/sign` response's `maxBytes` every time, never hardcoded (R1). Tags are server-normalized (trim/lowercase/dedupe) — the UI re-renders whatever the server returns rather than fighting it client-side. Legacy seed rows with `fileUrl: null` render without a download/preview action.
**⚠️ Known backend bugs found via direct verification (2026-07-21, not yet fixed, flagged to Hassan):** (1) `POST /content/confirm` returns `500 Internal server error` even on a contract-valid body after a genuinely successful sign+PUT. (2) `GET /content` always returns `content: []` regardless of filters, while `pagination.total`/`typeCounts` report correct real counts — there is also no per-item `GET /content/:id`, so a content row currently cannot be read back from this API at all. Both are covered by dedicated regression tests in `content-library.full.spec.ts` (real API, expected RED until fixed); all other tests there mock the sign/PUT/confirm/list calls so the UI itself is verified independent of these two bugs.
Mutations: `content.confirm` (upload) / `content.update` / `content.delete` (→ §5.4 content row: `['content-library']` + `['courses', id]` when course-scoped).

## Tab: Live Sessions (`?tab=live`) — `['live-sessions', filters]` (doc §12–§15)
**Status: `[built]` 2026-07-21 — v1 (REAL Zoom integration)**, contract `LIVE_SESSIONS_CONTRACT.md`. `LiveSessionsTab.tsx` + `liveSessionsApi.ts` + types `liveSessions.ts`.
Create form: title, instructor (required, real INSTRUCTOR user via `['users']` filtered by role, per R2), start time (must be future, validated client-side), duration (5–1440 min, default 60), timezone (IANA, default UTC), optional course link, description, max participants. `provider` is ZOOM-only in v1 — no provider picker is rendered at all (Meet/Teams/Other are typed for forward-compat but never offered).
**GAP vs this doc's prior draft (reconciled 2026-07-21):** the doc previously listed manual `liveSession.start`/`liveSession.end` actions and a post-session `liveSession.recording.attach` mutation. The real v1 contract has NO manual status control anywhere — `status` (UPCOMING/LIVE/ENDED) is 100% server-derived from `startTime`+`durationMin` and self-corrects on every read; sending `status` in a PATCH is a 400. Recording upload is not in v1 scope. Those mutation IDs are removed below in favor of the three that actually exist.
`startUrl` is the Zoom HOST link — rendered ONLY behind an admin-only "Start (host)" action, visually distinct from "Join" (which opens `joinUrl`, nothing else — no SDK/embed) — never exposed anywhere else. Until Zoom credentials are configured server-side, `POST`/schedule-changing `PATCH` return `503` with a message rendered verbatim in an info banner (expected v1 state, confirmed live against the dev server on 2026-07-21 — reads and validation work regardless); a `502` (transient Zoom API failure) renders as a distinct, retry-suggested error.

## Tab: Enrollments (`?tab=enrollments`) — `['enrollments', entityId?]` (doc §2, Students doc §3)
**Status: `[built]` 2026-07-21 — v1**, contract `ENROLLMENTS_CONTRACT.md`. `EnrollmentsTab.tsx` + `enrollmentsApi.ts` + types `enrollments.ts`. Rides the EXISTING `course_enrollments` table — the same rows behind the LM KPIs, enrollment trend chart, top-courses, and the Courses tab's `enrolledCount`, so every write here invalidates the FULL IMPACT_MAP §5.2 row, never a subset.
Status enum is the existing one (`NOT_STARTED`/`IN_PROGRESS`/`COMPLETED`/`OVERDUE` — no `DROPPED` in v1). `progress` is learner-derived and read-only — the status-update payload type has no `progress` field at all (structural, not conventional), so a status change can never carry it. Marking `COMPLETED` stamps `completedAt` only; it does not set `progress` to 100 client-side. `course.enrollmentLimit` is enforced server-side — the exact "Course is full…" message renders directly above the Enroll dialog's submit button, never as a toast. Unenroll (`DELETE`) does NOT revoke an already-issued certificate; confirm copy stays neutral. Status chips share every active filter except status (same pattern as the Courses tab), reading `statusCounts` from the same GET response (never computed client-side).
Mutations: `enrollment.create` (Enroll dialog) / `enrollment.statusUpdate` (status-only PATCH) / `enrollment.cancel` (unenroll) — → IMPACT §5.2, full row every time.
